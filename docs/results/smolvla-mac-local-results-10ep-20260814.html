再現性上の制約

環境seedは対応しているがpolicy RNGは評価全体で連続する。成功時の早期終了により後続episodeのpolicy乱数系列がモデル間でずれるため、厳密な対応比較にはepisodeごとのRNGリセットが必要である。

03

考察

実測から確認できた事実

  • MacローカルMPSで2モデル合計200エピソードを完走した。
  • 全体成功数はBase 78、Spatial LoRA 77で、差は1成功だった。
  • task 3は8/10から6/10、task 8は8/10から5/10へ低下した。
  • task 6は7/10で同率、task 7は4/10から7/10へ改善した。
  • LoRA評価はBaseより1エピソード平均1.003秒長かった。

結果から考えられること

  • 全体−1ポイントは信頼区間を踏まえると明確な性能低下とは言えない。
  • 初回3試行の3タスク一律悪化は標本変動の影響が大きかった。
  • task 3の把持失敗傾向は残り、corrective data候補として優先度が高い。
  • task 8は初回の改善から今回の悪化へ反転しており、RNG依存と失敗段階の切り分けが必要である。
04

改善点

P1task 8の失敗を分類

失敗5件の動画と状態遷移を保存し、到達・把持・配置の失敗段階を確定する。分類前に追加配分を決めない。

P1policy RNGをepisode単位で固定

Torch・NumPy・Python RNGも各episode開始時に同じ値へ戻し、モデル間・試行数間で比較可能な評価にする。

P220 seed以上へ拡張

task 3・8を中心に20 seed以上へ増やし、20〜30ポイント差が再現するかを対応差と信頼区間で確認する。

P2データ配分を再設計

旧task 3・6・7への一律40%配分は採用しない。task 3と分類後のtask 8をcorrective候補、task 6・7をrehearsalとする。

P3段階別指標を保存

成功率に加えて到達率、把持率、搬送率、配置述語達成率を保存し、失敗段階の移動を検知する。

P3評価時間を交互順で測定

Macの温度・負荷を揃え、Base/LoRAの実行順を交換して+1.003秒/episodeが再現するか確認する。
